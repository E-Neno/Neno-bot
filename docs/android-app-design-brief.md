# Neno Android App Design Brief

> 状态日期：2026-06-23
> 本文是 Android 原生 App v0 的产品与设计输入，不是 UI 设计稿，也不是实现计划。

## 1. 核心判断

Neno Android App 的第一目标不是提高聊天效率，也不是做一个更好看的 AI 工具。

第一目标是：让用户在手机里感到 Neno 是一个持续存在的对话对象，而不是一个等用户打开的功能入口。

## 2. 已确定方向

第一屏采用对话列表，而不是聊天输入框、角色展示页或功能首页。

Neno 是置顶的主联系人。其他 AI 可以作为后续添加的辅助联系人或工具型对话对象存在，但不能把 Neno 稀释成普通 bot。

```text
对话
  - Neno：置顶主联系人
  - 写作助手：可选工具联系人
  - 代码助手：可选工具联系人
  - 临时聊天：可选工具联系人

Neno 聊天
  - 私密持续对话
  - 关系连续性
  - 延迟 / 睡眠 / 稍后回复节奏

助手聊天
  - 任务型 AI 对话
  - 与 Neno 清晰分离
```

用户可见界面默认使用中文。英文只用于代码命名、内部协议、调试字段和开发文档；App 内的标题、按钮、状态、通知、错误文案、权限说明都应先写中文。

## 3. 反目标

App 不应像：

- ChatGPT 首页
- 客服聊天
- 后台控制台
- SaaS dashboard
- 二次元恋爱游戏
- 虚拟人养成页
- 功能很多的工具箱
- 只有一个输入框的 AI wrapper

尤其不要把第一屏做成“她在客厅 / 她正在做什么”的角色状态展示。那会把 Neno 推向虚拟人，而不是真实对话对象。

## 4. 第一屏原则

第一屏是对话列表，用真实沟通软件的心智模型承载 Neno。

Neno 列表项需要表达：

- 她是固定存在的主联系人
- 最近一次对话停在哪里
- 是否有未读或未完成的话
- 当前是否可继续说话
- 她是否刚回来过或稍后会回

其他 AI 列表项需要表达：

- 它们是工具型对象
- 它们不和 Neno 竞争情感位置
- 它们可以被添加、隐藏或弱化

## 5. Neno Chat 原则

Neno 的聊天页不是普通 AI 聊天框。

需要保留：

- 对话连续性
- 非秒回节奏
- 睡眠、忙碌、稍后回复等状态
- 用户和 Neno 之间的关系感

不要在聊天页展示调试状态、世界 JSON、控制按钮或后台面板。

如果需要呈现世界状态，只能以低干扰方式出现，例如一句自然状态提示，而不是房间面板或角色仪表盘。

## 6. 通知原则

通知负责“她出现”，不负责完成主要聊天。

v0 不优先做通知快捷回复。快捷回复可以保留为未来可选能力，但它不是核心体验。

通知更应该表达：

- 她回来了
- 她想起了一句话
- 她晚点再回
- 她现在不适合继续聊

点开通知后进入 App 内对话，而不是在通知栏完成关系交互。

## 7. 视觉设计工作流

Codex / Claude 不直接凭空设计最终 UI。

推荐流程：

1. 先使用本文作为设计输入。
2. 产出 2-3 个视觉方向稿或低保真 wireframe。
3. 用户按“像不像坏方向”做反向验收。
4. 方向确认后，再转成 Android Compose 组件。
5. 实现阶段必须用截图或真机画面对照设计稿。

实现者职责是转译和验证，不是自由发挥视觉风格。

### 7.1 已确认视觉方向

当前视觉方向已确认，不再继续大范围生成新方向稿。

方向为 A + D：

- A：更像真实聊天软件。第一屏是日常可用的对话列表，而不是概念首页。
- D：更 Android 原生。优先贴近 Material 3、系统字体、原生顶部栏、列表行、输入框和触控节奏。

视觉基准：

- 浅色模式，不使用深色概念风格。
- 暖白 / 浅灰背景，近黑正文，中性灰辅助文字。
- 少量暖色强调只用于 Neno 的未读、在线或置顶提示。
- Neno 作为置顶联系人更重要，但不做夸张卡片、不做角色页。
- 不放右下角写信笔、悬浮创建按钮或无意义装饰按钮。
- 不使用赛博、虚拟人、房间、角色养成、深色信号轨或抽象符号风格。

后续实现只能在该方向上微调头像、列表节奏、输入框、气泡颜色和中文文案，不应重新发散视觉风格。

## 8. v0 屏幕范围

v0 只覆盖最小可用 App 体验：

- 对话列表：首页，Neno 置顶，其他 AI 作为弱化的工具联系人或占位联系人。
- Neno 聊天页：持续私密对话，保留延迟回复和状态提示的空间。
- 设置 / 连接状态页：账号、后端连接、通知权限、基础诊断入口。

v0 可以预留工具联系人，但不做完整多 AI 市场、复杂联系人管理或多工作区。

## 9. Android 技术边界

目标技术栈：

- Kotlin
- Jetpack Compose
- Android 原生工程
- 目录建议为 `mobile/android/`

不使用：

- Expo
- React Native
- WebView 包网页
- `/test` 控制台作为产品前端

## 10. 后端边界

Android App 需要面向移动端的 API 层。不要直接复用 debug 控制台语义。

后续需要明确：

- 设备鉴权
- 会话 token
- 发送消息接口
- 拉取对话列表接口
- 拉取 Neno 当前对话摘要接口
- 拉取消息历史接口
- 主动消息和通知投递机制

聊天侧仍必须遵守现有后端约束：不能绕过 Session 串行模型，不能让 App 直接写 `life_world_state`，不能破坏 prompt 装配顺序。

## 11. v0 不做什么

- 不做完整多 AI marketplace
- 不做角色养成系统
- 不做世界地图或房间展示首页
- 不做控制台能力
- 不做复杂主题系统
- 不做 iOS
- 不做通知快捷回复作为核心能力

## 12. 下一步

下一步不是继续生成视觉方向稿，而是把本 brief 固定为 Android v0 的产品输入。

进入 Android 工程前，先补一份实现计划，明确：

- `mobile/android/` 工程结构
- Compose 页面拆分
- 本地状态模型
- 移动端 API 需求
- 与现有后端 Session 串行模型的边界
- 真机或模拟器验证方式

实现阶段必须保持中文界面，并以已确认的 A + D 视觉方向为准。
